# <ハーネス名> 計画書（雛形）

harness-testing-framework（htf）の上に実ハーネスを作る時の計画書の骨格（完成版、v1.0）。各節の「書くこと」に答える形で埋め、「完了条件」は実行できる検査で書き、結果を併記する。実例は `examples/software-factory/docs/plan.md`（この雛形を当てはめたもの。版 0.2）。

読む順: `docs/adopting.md` → この雛形 → `examples/software-factory/`（実例。`examples/toy-minimal/` は最小の実例）。htf 本体の実装は読まない。この雛形と adopting.md で判断できないことは、ハーネスの `docs/adopting-gaps.md` に書いて続行する。htf 本体を直したり、ハーネスの中で回避したりしない。

進め方はこの節の順で、各節を一つの作業単位にする。進捗はハーネスの `docs/progress.md`（先頭に「次にやること」、日付ごとに「完了したこと」「未完了と理由」「発見した問題（ワークフロー定義 / htf 本体）」「実行した検証とその結果の要旨」）。完了条件は実装より先に書き、実装前に失敗することを記録してから実装する。運用に入ってからの手順は htf の `docs/maintenance.md`。

## 0. 前提

- 書くこと: ハーネス名、目的、ワークフローの概要（フェーズとステージの一覧、ユーザー待ちの箇所、動的に数が決まる下位作業）。固定の設計判断（adopting.md 第 1・2 節: 三層、評価順序、記述が分類の全て、carry の restore + overlay、仕様が唯一の情報源）。本体が使う基準値（カバレッジの基準など）は定義から読む約束
- 完了条件: ディレクトリ骨格がある。`workflow.yaml`（子があれば子の定義）、`stages/`（本体）、`metrics/`（レジストリとマニフェスト）、`user/`（シミュレータ）、`fixtures/`（本体が使う成果物・コードベース・ペルソナ・台本・確率的な構成）、`tests/`（テストと、expectations・E2E 計画）、`docs/`（計画書、progress.md、adopting-gaps.md）
- 実例: software factory 第 0 節（5 フェーズ 9 ステージ + 子 3 の表、ユーザー待ち 2、子の集約）

## 1. ワークフロー定義

- 書くこと: `workflow.yaml`（子があれば子の定義）。フェーズと `goal`、各ステージの `artifacts`（reads / writes / memory_in / memory_out）、`goal`（quantitative は指標名と基準、qualitative は自然言語。基準値は定性にも書く）、`end_state`（成果物から観測できる条件。互いに排他。重なりうる時は記述中に「〜に優先する」。`unknown` を必ず含む）、`rollback`（戻り先は前方、`carry`、`max`）、`user_input`、`subworkflow`。分類体系の版 `workflow.version`。成果物の形（各ファイルの鍵）の取り決め
- 守ること（adopting.md 3.1。software factory の往復と第三者レビューで繰り返し出たもの）:
  - 最初のステージは unknown 以外の end_state を持てない。直させたい失敗は後ろの「検出するステージ」で判定し、そこから「直すステージ」へ戻す（検出と修正を分ける。実例: 子の code → check → unit_test、親の implement → integrate）
  - 二段以上続けて戻る経路では、各辺の carry に「戻り先より後ろへ運ばれうる鍵」も載せる（閉包）。閉包をテストで固定する
  - goal の定性は原本（reads）との一致を要求し、自分の写しだけを基準にしない。基準値（0.85 など）、0 件の境界、kind の取りうる値、id の維持の約束、空の回答の扱いを記述に書く
  - 大きな成果物は要旨（印、失敗の一覧、件数、適用した基準）を先頭か小さな専用ファイルに置き、全結果は別ファイルにする（状態文書は 1 ファイル 4000 文字で切られる）
- 完了条件: `python -m htf.testing.spec workflow.yaml --metrics <manifest>` が 0 件。人間の MECE レビュー（観測可能か、排他か、各 end_state に戻り先があるか）に出す前に、実装していない第三者に定義 2 ファイルだけを読ませる（読取範囲は指示ではなく隔離ディレクトリで課す。既存の指摘は渡さない）。指摘は表（重大度 / 対象 / 指摘 / 根拠の引用 / 失敗する場面 / 分類体系が変わるか / 提案）にし、採否は人間
- 止まる条件: end_state の追加・分割・統合・意味変更は人間の承認。記述は v0（仮説）で、実行の観測と人手ラベルで改訂する。採る時は `workflow.version` を上げ、台本・E2E 計画・expectations を合わせる（maintenance.md 第 3 節の順）
- 実例: software factory 第 1 節と第 1.1 節（11 件 + Codex の 9 件の指摘と採否、版 0.1 → 0.2）

## 2. 最初の実ステージの選択

- 書くこと: 最初に本物にする（LLM や実ツールを使う）ステージ一つと、その理由（成果物が観測しやすい、指標が決定論的に実装できる、end_state が少ない）。他のステージは偽本体のまま。LLM を使わないハーネスでは「本物」は実ツールを走らせるステージと読み、第 4・5 節は偽の正解と偽の分類器での実施に留めてその旨を書く。実ツールは作業ディレクトリに書かない（キャッシュは一時ディレクトリへ）、出力は時刻と絶対パスを落として正規化する、内容のハッシュでメモ化する
- 完了条件: そのステージの指標がレジストリにあり、変種ごとに本物の値を返す。偽本体の台本で 7 種の遷移が通る（adopting.md 3.9）。LLM 呼び出しは recorder を経由し、記録を残す（記録 → 再生でスナップショットの digest が一致する）
- 実例: software factory 第 2 節（子の check と unit_test。`toolchain.py`）

## 3. フィクスチャとコーパス

- 書くこと: 決定論的な偽本体が使うフィクスチャ（正しい成果物、壊れた成果物、曖昧な入力）、ユーザーシミュレータのペルソナ（3 以上。中断するペルソナはそのステージの最初の質問から保留する）、台本（各ステージの各 end_state を誘発できる組。規則は README に）、確率的偽本体の構成（既知の分布。再進入で分布が変わるもの、クラス内で代表ごとに下流が分かれるもの）
- 完了条件: E2E 計画（`htf.testing.e2e`）が親子の全 (stage, end_state) を誘発か注入で踏む。carry を運ぶ end_state は誘発で踏む。フィクスチャの世界で起きないクラスは無理に作らず、注入で踏んで本体の論理を手作りの成果物で単体テストし、その旨を計画に書く。契約適合テスト（`htf.contract.conformance`）を通す
- 実例: software factory 第 3 節（台本 26、ペルソナ 5、43 対象 誘発 39・注入 4、誘発できない 3 クラス）

## 4. 人手ラベル

- 書くこと: コーパスの作り方（トリアージ待ち行列から、またはフィクスチャから）、ラベラー、件数の目安（ステージ × クラスごとに 20 件以上）、ラベルの形式（`htf.testing.oracle` の JSONL。`workflow_version` を持つ）
- 完了条件: ラベル付きコーパスがある。`human_approval` 指標が要るステージは人間に委ねる旨を書く。人手ラベルが無い段階では、偽の正解（本体が本物の結果から書いた印）で代用していることを明記する
- 実例: software factory 第 4 節

## 5. 分類器検証

- 書くこと: 分類器の後ろ側（htf の ADR-006 に従う）、κ・ECE・再実行一致の目標と閾値（仮置き。根拠を記録）、同じ文書が多いコーパスでの有効標本の扱い
- 完了条件: オラクル検証レポート（`htf.testing.oracle.verify_oracle`）。閾値は較正結果から決め、根拠を記録する。ベンダーの主張は自分のコーパスで確かめる。CI のナイトリーの段（`-m oracle`）に載せる
- 実例: software factory 第 5 節（偽の分類器のみ）

## 6. 分布テストと往復

- 書くこと: expectations（N、種、`workflow_version`、(stage, 初回 / 再進入) ごとの区間、run 全体の結果の区間。区間は理論値 ± 約 3 標準誤差で、根拠をファイル冒頭に）、確率的偽本体または実 LLM（recorder 経由）、記述の改訂の往復の手順（改訂のたびに整合性検査。分類体系の変更は人間の承認と版上げ）
- 完了条件: expectations が通る。ずらした expectations が落ちることも確かめる。定義の版と expectations の版が一致する（runner が照合する）
- 実例: software factory 第 6 節（版 0.2 の実測と理論値）

## 7. 独立性

- 書くこと: 検証するクラスと代表の鍵（既定は戻り先へ運ぶ carry。識別しないクラスは検証できないので、別の鍵を与えるか記録する）、p 値の閾値（仮置き）
- 完了条件: クラス内で下流の分布が揃う（分割が検出されたら、クラスの粒度を変える提案を書いて止まる）
- 実例: software factory 第 7 節（markov は検出なし、split は検出、検証不能なクラスの記録）

## 8. 残りのステージと E2E

- 書くこと: 残りのステージを本物にする順、E2E 計画の更新（誘発 / 注入）、マルコフ合成との比較（子を持つステージは子 run 数の分布も）
- 完了条件: (stage, end_state) のカバレッジ 100%、マルコフ予測と実測が許容差内（マルコフ性が成り立たない構成では外れることも確かめる）
- 実例: software factory 第 8 節

## 9. 維持ループ

- 書くこと: トリアージの頻度と担当、記述改訂の承認の流れ、分類体系の版（`workflow.version`）とハーネスの版の同期（同じ変更で上げる。expectations・計画・コーパスの `workflow_version`）、CI の段階（整合性検査と決定論テストは常時、オラクル検証はナイトリー、分布と E2E は手動）
- 完了条件: 維持の手順書がある（htf の `docs/maintenance.md` を基にハーネス固有の担当と頻度を書く）。実 LLM を入れる前の段階では、担当と頻度を仮置きにしてその旨を書けばよい（第 2 節の読み替えと同じ形）
- 実例: software factory 第 9 節

## 付録: 止まる条件と禁止事項

- 止まる: 分類体系・閾値・スキーマの意味の変更、同じ戻りの上限超過（作業の進め方の規則。ある節から前の節へ差し戻すのが仕様へは 3 回、それ以外は 2 回まで。ワークフローの `max` のことではない）、LLM の予算上限、人手ラベルや承認が要る、破壊的操作
- しない: 完了条件や閾値を緩めて通す、テストをスキップ、未決事項を黙って決める、end_state を増やして分類を通す、ワークフロー定義を読まずに本体を書く、コーパスやスナップショットをそのまま読み込む、実行結果を残さずに「できた」と書く、htf 本体を直す・ハーネスの中で回避する（adopting-gaps.md に書く）
