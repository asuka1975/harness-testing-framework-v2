# <ハーネス名> 計画書（雛形）

harness-testing-framework（htf）の上に実ハーネスを作る時の計画書の骨格。**最低限版**（F4 の入口用。F5 で software factory を実例にした完成版にする）。各節の「書くこと」に答える形で埋め、「完了条件」は実行できる検査で書く。

読む順: `docs/adopting.md` → この雛形 → `examples/toy-minimal/`（実例）。htf 本体の実装は読まない。この雛形と adopting.md で判断できないことは、ハーネスの `docs/adopting-gaps.md` に書いて続行する。htf 本体を直したり、ハーネスの中で回避したりしない。

進め方はこの節の順で、各節を一つの作業単位にする。進捗はハーネスの `docs/progress.md`（先頭に「次にやること」、日付ごとに「完了したこと」「未完了と理由」「発見した問題（ワークフロー定義 / htf 本体）」「実行した検証とその結果の要旨」）。

## 0. 前提

- 書くこと: ハーネス名、目的、ワークフローの概要（フェーズとステージの一覧、ユーザー待ちの箇所、動的に数が決まる下位作業）。固定の設計判断（adopting.md 第 1・2 節: 三層、評価順序、記述が分類の全て、carry の restore + overlay、仕様が唯一の情報源）
- 完了条件: ディレクトリ骨格（`workflow.yaml`、`stages/`、`metrics/`、`user/`、`fixtures/`、`tests/`、`docs/`）がある

## 1. ワークフロー定義

- 書くこと: `workflow.yaml`（子があれば子の定義）。フェーズと `goal`、各ステージの `artifacts`（reads / writes / memory_in / memory_out）、`goal`（quantitative は指標名と基準、qualitative は自然言語）、`end_state`（成果物から観測できる条件。互いに排他。重なりうる時は記述中に「〜に優先する」。`unknown` を必ず含む）、`rollback`（戻り先は前方、`carry`、`max`）、`user_input`、`subworkflow`。分類体系の版 `workflow.version`
- 完了条件: `python -m htf.testing.spec workflow.yaml --metrics <manifest>` が 0 件。人間の MECE レビュー（観測可能か、排他か、各 end_state に戻り先があるか）に出す前に、実装していない第三者に読ませる
- 止まる条件: end_state の追加・分割・統合・意味変更は人間の承認。記述は v0（仮説）で、実行の観測と人手ラベルで改訂する

## 2. 最初の実ステージの選択

- 書くこと: 最初に本物にする（LLM や実ツールを使う）ステージ一つと、その理由（成果物が観測しやすい、指標が決定論的に実装できる、end_state が少ない）。他のステージは偽本体のまま
- 完了条件: そのステージの指標がレジストリにあり、偽本体の台本で 7 種の遷移が通る（adopting.md 3.9）。LLM 呼び出しは recorder を経由し、記録を残す

## 3. フィクスチャとコーパス

- 書くこと: 決定論的な偽本体が使うフィクスチャ（正しい成果物、壊れた成果物、曖昧な入力）、ユーザーシミュレータのペルソナ（3 以上）、台本（各ステージの各 end_state を誘発できる組）、確率的偽本体の構成（既知の分布。再進入で分布が変わるもの）
- 完了条件: E2E 計画（`htf.testing.e2e`）が親子の全 (stage, end_state) を誘発か注入で踏む。契約適合テスト（`htf.contract.conformance`）を通す

## 4. 人手ラベル

- 書くこと: コーパスの作り方（トリアージ待ち行列から、またはフィクスチャから）、ラベラー、件数の目安、ラベルの形式（`htf.testing.oracle` の JSONL）
- 完了条件: ラベル付きコーパスがある。`human_approval` 指標が要るステージは人間に委ねる旨を書く

## 5. 分類器検証

- 書くこと: 分類器の後ろ側（htf の ADR-006 に従う）、κ・ECE・再実行一致の目標と閾値（仮置き。根拠を記録）
- 完了条件: オラクル検証レポート（`htf.testing.oracle.verify_oracle`）。閾値は較正結果から決め、根拠を記録する。ベンダーの主張は自分のコーパスで確かめる

## 6. 分布テストと往復

- 書くこと: expectations（N、種、(stage, 初回 / 再進入) ごとの区間、run 全体の結果の区間）、確率的偽本体または実 LLM（recorder 経由）、記述の改訂の往復の手順（改訂のたびに整合性検査。分類体系の変更は人間の承認）
- 完了条件: expectations が通る。ずらした expectations が落ちることも確かめる

## 7. 独立性

- 書くこと: 検証するクラスと代表の鍵（既定は戻り先へ運ぶ carry。識別しないクラスは検証できないので、別の鍵を与えるか記録する）、p 値の閾値（仮置き）
- 完了条件: クラス内で下流の分布が揃う（分割が検出されたら、クラスの粒度を変える提案を書いて止まる）

## 8. 残りのステージと E2E

- 書くこと: 残りのステージを本物にする順、E2E 計画の更新（誘発 / 注入）、マルコフ合成との比較（子を持つステージは子 run 数の分布も）
- 完了条件: (stage, end_state) のカバレッジ 100%、マルコフ予測と実測が許容差内

## 9. 維持ループ

- 書くこと: トリアージの頻度と担当、記述改訂の承認の流れ、分類体系の版とハーネスの版の同期、CI の段階（整合性検査と決定論テストは常時、オラクル検証はナイトリー、分布と E2E は人間の許可時）
- 完了条件: 維持の手順書がある（htf の `docs/maintenance.md` は F5）

## 付録: 止まる条件と禁止事項

- 止まる: 分類体系・閾値・スキーマの意味の変更、同じ戻りの上限超過（仕様へは 3 回、それ以外は 2 回）、LLM の予算上限、人手ラベルや承認が要る、破壊的操作
- しない: 完了条件や閾値を緩めて通す、テストをスキップ、未決事項を黙って決める、end_state を増やして分類を通す、ワークフロー定義を読まずに本体を書く、コーパスやスナップショットをそのまま読み込む、実行結果を残さずに「できた」と書く
