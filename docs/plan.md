# harness-testing-framework 構築計画書

Oct 21, 2026 · @asuka1975

## 1. 目的とスコープ

この文書は、ワークフロー型エージェントハーネスのための汎用テスティングフレームワーク harness-testing-framework（以下「フレームワーク」）を構築するための、AI エージェント（Claude Code）向けの指示書である。対象はフレームワークのリポジトリ一つ。実ハーネスへの適用はこの計画の範囲外とし、代わりに適用の手引き（adopting.md）とハーネスごとの計画書の雛形をフレームワークの成果物として用意する。

- フレームワーク本体: ワークフロースキーマ、ハーネス契約、整合性検査器、参照ランタイム、テストランナー群、運用ツール。特定のハーネスに依存せず、今後作るすべてのワークフロー型ハーネスがこれを使う
- 玩具ワークフロー二つ: toy-minimal（契約と全遷移種別を最小構成で覆う）と software factory（ソフトウェア開発のワークフローを模し、実在の決定論指標を持つ玩具。adopting.md だけを読んで作れることの証明を兼ねる）
- 適用のための文書: adopting.md（ハーネス側が満たすべきこと）と harness-plan-template.md（実ハーネスごとの計画書の雛形）

フレームワーク自身のテストデータは、二つの玩具ワークフロー（決定論的な偽ステージ本体と、種を固定した確率的な偽ステージ本体）と、スキーマの正例・負例である。フレームワークのテストはすべて LLM なしで通る。玩具で確かめられるのは機構（ランナーが計算を間違えていないこと）であり、方法そのもの（自然言語の end\_state を分類器が人間と一致して分類できるか、マルコフ性が成り立つか、carry で往復が収束するか）の検証は実 LLM を伴う別の作業で、その場所は決定 #6 で決める。

作らないもの（2ステージ分の実データが出るまで判断しない）: 汎用のクラススキーマ設計、Alloy / TLA+ 等の形式手法ツールの導入、Jev 以外の分類器の調査、フェーズ間の組み合わせテスト。

完成の定義: 二つの玩具に対して全テストランナーが LLM なしで通り、参照ランタイムが契約適合テストを通り、software factory が adopting.md と雛形だけから作られたことが示され、v1.0 としてバージョンつきで公開されている。

## 2. 固定された設計判断

これまでの議論で合意済みの前提。エージェントは再検討せず、矛盾を見つけたら作業を止めて人間に報告する。

| 判断 | 決定内容 | エージェントへの帰結 |
| --- | --- | --- |
| フレームワークとハーネスの境界 | フレームワークは契約を定める。契約は三つの操作（run(stage, snapshot) → snapshot、evaluate(stage, snapshot) → class、restore(snapshot) + overlay(carry)）、スナップショット形式、ステージ本体・指標・ユーザー入出力・LLM クライアントのインターフェースから成る。ハーネスは契約を満たすもの（ワークフロー定義、ステージ本体、指標の実装、ユーザー入出力、LLM クライアント）を提供する | ハーネス固有の名前や前提（特定のハーネス名、特定の定理証明器や外部ツール、特定のステージ名）をフレームワークに入れない。フレームワークの不足はフレームワーク側で直し、ハーネス内で回避しない |
| 終了状態の三層 | goal = 正常系（quantitative は決定論的述語、qualitative は自然言語）。end\_state = 準正常系（自然言語で MECE に分類し、各クラスに戻り先ステージが一意に決まる）。unknown = 例外系（人間に差し戻す） | ステージの結果は必ず三層のどれかに落ちる。end\_state を goal の言い換えにしない |
| 評価順序 | goal 指標 → goal 定性判定 → end\_state 分類 → unknown。一回の実行ごとに判定する | runner の evaluate はこの順序で実装し、変えない |
| 分類器 | goal と end\_state の記述をそのまま選択肢として渡して状態を分類させる。質問への分解や導出規則は書かない。後ろ側は Jev または System One アダプタ経由の LLM。確信度が閾値未満なら unknown | 分類ロジックをコードに書かない。記述が分類の全て |
| ロールバック | 戻り先の開始時スナップショットを復元し、その上に carry の項目だけを重ねる。辺ごとに max を持ち、超過は escalate | checkpoint は restore と overlay の二操作。carry の各項目は元ステージの memory\_out と戻り先の memory\_in に宣言する |
| 仕様は唯一の情報源 | ハーネスは実行時にワークフロー定義（YAML）を読んで遷移とゲートを駆動する。テストも同じファイルから生成する | ステージ順や遷移をコードに書かない。仕様の問題はローカルに回避せずワークフロー定義を直す |
| 分布基準の置き場 | 「N 回実行して goal 到達 80% 以上」のようなテスト合否基準は expectations に置く | ワークフロー定義に N や出現率を書かない |
| 非決定性の二層分離 | ハーネスのロジック（遷移・ゲート・ロールバック）は偽ステージ本体と記録再生で決定論的にテストする。統計的テストの対象は LLM の振る舞い分布だけ | フレームワークのテストは LLM を呼ばない。ステージ本体の LLM 呼び出しは recorder を経由する |
| end\_state 記述は仮説 | 事前に書く記述は v0。実行の観測と人手ラベルで改訂する。分類体系はハーネスと同じバージョンで管理する | 記述の改訂は人間の承認を経る。改訂のたびに整合性検査を通す |
| 組み合わせテストはしない | クラスは下流の振る舞いに関する同値類。同一クラス内の代表で下流分布が揃うこと（独立性）を検証する。E2E は各ステージの各 end\_state を一度は踏む | クラスの粒度は独立性検証の結果でのみ変える |
| 分類器の検証 | 人手ラベルのコーパスとの一致率（Cohen の κ）と較正（ECE）で測る。ベンダーの主張は自分のコーパスで確かめる | 閾値は較正結果から決め、根拠を記録する |

## 3. 未決事項（着手前に人間が決める）

十件。#6 以外はフレームワークの決定で、F1 の最初のタスクでエージェントが選択肢と帰結を docs/decisions.md の下書きとして提示し、決定を待つ。#6 は F5 の終わりに決める。決定は ADR 形式で記録し、先送りする場合は「強制点」のマイルストーンで決めざるを得なくなることを明記する。

| --- | --- | --- | --- | --- |

| 3 | escalate 後の人間の選択肢 | 再実行 / 指定ステージへロールバック / goal 到達扱いで続行（注記つき）/ 中止 | 四つすべて。runner はこの四つを受け付ける | F2 runner |
| 4 | ユーザー回答待ちの表現 | (a) end\_state の一つとして持つ (b) runner が中断状態を持ち、ステージ本体はユーザー入出力インターフェースで同期的に待つ | (b)。テストではそこにシミュレータを束縛する | F2 runner |

## 4. リポジトリ構成と成果物

リポジトリ一つ。フレームワーク本体（schema / contract / runtime / testing）は特定のハーネスを知らず、玩具は examples/ の下に閉じる。testing/ 以下はランナーの実装で、テストデータ（フィクスチャ、expectations、コーパス）は各玩具と、将来の実ハーネス側に置く。開始時に存在するのは docs/plan.md だけでよく、残りは F1 の初期化タスクで作る。基底スキーマは付録 A にあり、ステージ定義の書き方は付録 B にある。

```text
harness-testing-framework/
  schema/
    workflow.schema.json           拡張スキーマ（carry / max / artifacts / 指標の形）
    examples/                      正例・負例。検査器のテストデータ
  contract/                        ハーネス契約。インターフェース、スナップショット形式、契約適合テスト
  runtime/                         参照ランタイム（決定 #8）。loader / checkpoint / runner / oracle / recorder
  testing/
    spec/                          整合性検査器
    harness/                       偽ステージ本体によるランナー検証のランナー
    oracle/                        コーパス形式、ラベル形式、一致率・較正・安定性のレポート
    stages/                        分布テストランナー、expectations 形式
    e2e/                           カバレッジ計画（誘発と注入）、マルコフ合成
    triage/                        unknown と低確信度のトリアージ待ち行列
  examples/
    toy-minimal/                   玩具 1。3〜4ステージ。契約と全遷移種別を最小構成で覆う
      workflow.yaml
      stages/                      決定論的な偽ステージ本体、確率的な偽ステージ本体
      tests/                       fixtures、expectations
    software-factory/              玩具 2。ソフトウェア開発のワークフロー。adopting.md だけを読んで別セッションで作る
      workflow.yaml
      stages/                      偽ステージ本体。実装とテストのステージは fixtures のコードベースに実際にビルドとテストを走らせる
      metrics/                     指標レジストリの実装（ビルド通過、テスト通過、カバレッジ、lint、変更パスの範囲）
      user/                        ユーザーシミュレータ（要求の取り込みで使う）
      fixtures/                    小さなコードベース、要求の入力、ペルソナ
      tests/                       expectations、E2E 計画
      docs/adopting-gaps.md        adopting.md と雛形だけでは判断できなかったことの記録
  docs/
    plan.md                        本書
    decisions.md                   決定記録（ADR）
    progress.md                    エージェントの作業ログ
    adopting.md                    ハーネス側が満たすべきことの手引き（F2 で初版、F5 で完成版）
    harness-plan-template.md       実ハーネスごとの計画書の雛形（F5）
```

docs/progress.md の形式は固定する。先頭に「次にやること」、続いて日付ごとに「完了したこと」「未完了と理由」「発見した問題（ワークフロー定義の問題と、フレームワーク本体の不足を分けて）」「実行した検証とその結果の要旨」。エージェントはこのファイルを読んで再開し、書いて終わる。

## 5. エージェントループ

エージェントはハーネスと同じ三層の規律で動く。タスクの結果は、完了条件を満たした正常、既知の戻る条件に該当した準正常、どちらでもない例外のいずれかに落ち、準正常は指定の戻り先へ、例外は人間へ送る。

準正常は持ち帰る情報を記録して戻り先のタスクへ戻り、同じ戻りが上限を超えたら例外として人間へ送る。人間の決定後は読むところから再開する。

### 5.1 作業の単位

第6節のマイルストーンをタスクに分ける。タスクは一回の作業セッションで完了条件を実行して確かめられる大きさにし、着手時に progress.md の「次にやること」に列挙する。

### 5.2 セッションの開始と終了

開始時に docs/plan.md、docs/decisions.md、docs/progress.md をこの順で読み、progress.md の「次にやること」から再開する。例外は F4 の software factory を作るセッションで、第7節の二つ目のプロンプトに従い、adopting.md と雛形だけを読む。終了時に progress.md（F4 のセッションは examples/software-factory/docs/progress.md）を更新してから終わる。完了したこと、未完了と理由、発見した問題、実行した検証の要旨、次にやること。コンテキストを跨いで状態を保つ手段はこのファイルだけなので、更新せずに終わらない。

### 5.3 タスクのループ

1. 読む: 該当マイルストーンの節、関係する仕様（schema.json / workflow.yaml）、decisions.md の関連項目
2. 完了条件を先に実行可能にする: テスト、検査スクリプト、または具体的な確認手順を実装より先に書く。第6節の完了条件がそのまま使えるものはそれを使う
3. 実装する
4. 検証する: 2 で書いたものを実行する。整合性検査と決定論テスト（偽ステージ本体によるランナー検証）はタスクの種類に関わらず毎回実行する
5. 判定する
   - 正常: 完了条件を満たす。progress.md に記録して次のタスクへ
   - 準正常: 第6節の「戻る条件」のいずれかに該当する。持ち帰る情報（違反一覧、混同したクラス対、足りない宣言など）を progress.md に書いてから戻り先の作業に移る。同じ戻り先への差し戻しは仕様へは3回、それ以外は2回まで。超えたら人間へ
   - 例外: どちらでもない。5.5 の手順で人間へ
6. 記録する: progress.md

### 5.4 仕様への差し戻し

後段で見つけた問題は、出どころで二つに分ける。ワークフロー定義の問題（記述が曖昧、指標が決定論的に実装できない、クラスが粗い、carry が足りない、成果物宣言が無い）は、そのハーネスの workflow.yaml を直す。直した後は必ず整合性検査を通し、理由をコミットメッセージと progress.md に残す。分類体系の変更（end\_state の追加・分割・統合・記述の意味変更）は人間の承認が要るので、提案を書いて止まる。フレームワークの問題（契約で表せない操作、スキーマの表現力不足、ランナーや expectations 形式の不足）は、ハーネス内で回避パッチを書かず、まず玩具ワークフローで同じ問題を再現するテストを書き、フレームワークのリポジトリで直してテストを通し、バージョンを上げ、ハーネス側の依存を更新する。

### 5.5 止まって人間に聞く条件

次のいずれかに当たったら作業を止め、状況、選択肢、推奨、各選択肢の帰結を書いて待つ。決定を待つ間は他の独立したタスクに進んでよい。

- 第3節の未決事項に触れる判断が必要
- 分類体系の変更、閾値の変更、スキーマの意味変更
- 同じ戻りが 5.3 の上限を超えた
- LLM 呼び出しのコストが予算上限に達する
- 人手ラベルや承認（human\_approval 指標）が必要
- 破壊的操作（コーパスやレポートの削除、履歴の書き換え）

### 5.6 禁止事項

- 完了条件や閾値を緩めて通す
- テストをスキップまたは無効化して進む
- 未決事項を黙って決める
- end\_state を増やして分類を通す
- ワークフロー定義を読まずにステージ本体を書く
- コーパスやスナップショットをそのままコンテキストに読み込む（投影か要約を経由する）
- 「できた」と書く前に実行した結果を残さない

### 5.7 検証、コスト、並列化

完了条件はできる限り実行可能な検査で書き、実行したコマンドと出力の要旨を progress.md に残す。実行できない完了条件（human\_approval）は人間に委ねる。LLM 呼び出しはすべて recorder を経由し、記録があれば再生を使う。整合性検査と決定論テストは常時、オラクル検証は許可時かナイトリー、分布テストと E2E は人間が明示的に許可した時だけ実行する。独立したタスク（フィクスチャ作成とランナー実装など）はサブエージェントに分けてよいが、ワークフロー定義とスキーマの編集は一つのエージェントが直列に行う。高リスクの検証（分類器検証、分布基準の設定）は、実装したエージェントとは別のセッションかサブエージェントがレビューする。

### 5.8 汎用性の規律

- フレームワーク本体（schema / contract / runtime / testing）に、玩具や特定のハーネスの名前・前提（特定の定理証明器や外部ツール、特定のステージ名、特定の LLM）を書かない。必要になったら契約の属性か設定項目に一般化する
- 玩具固有のものは examples/ の下に閉じる。玩具の都合で本体を変える時は、変更を一般化した形で書き、両方の玩具で検証する
- software factory は adopting.md と雛形だけを読んで、別セッションで作る。作りながら本体を直してはいけない。足りなかったことは adopting-gaps.md に記録し、本体の修正は通常のセッションで行う
- 本体の修正は toy-minimal のテストで検証してから、software factory で再検証する
- 契約適合テストは参照ランタイムと、ハーネスが自前で用意した実装の両方が通す。ハーネスが契約を満たしているかはこのテストでのみ判定する

### 5.9 エージェントの役割

計画を実行するエージェントは五つの役割に分かれ、人間が三つの役割を持つ。役割ごとに読めるもの、書けるもの、起動できるもの、止まる条件が決まっている。保護ファイル（docs/plan.md、docs/decisions.md、schema/、contract/、各玩具の workflow.yaml と expectations）を書けるのは計画エージェントだけで、人間の承認が要るものは提案止まりにする。

| 役割 | 誰が | 読む | 書く | 起動する | 止まる条件 |
| --- | --- | --- | --- | --- | --- |
| 計画（オーケストレータ） | Claude Code の主セッション | plan / decisions / progress、本体すべて | progress.md、decisions.md の下書き、保護ファイル（唯一の編集者） | 実装・検証・調査の各エージェント、動的ワークフロー | 第5.5節の条件 |
| 実装 | 主セッション自身、または作業単位ごとのサブエージェント | タスクに必要な範囲 | 担当する本体コードと玩具の成果物。保護ファイルは不可 | なし（入れ子禁止） | 完了条件を満たせない。保護ファイルの変更が要る |
| 検証（第三者） | 実装を見ていない別セッションかサブエージェント | 完了条件、成果物、仕様 | reports/ のみ | なし | 証拠不足で判定できない |
| 利用者（F4） | 人間が起動する別セッション。再検証はサブエージェントでもよい | adopting.md、雛形、toy-minimal、公開 API の文書 | examples/software-factory/ のみ | 同じ読取制限を課したサブエージェント | adopting.md で判断できない事項は記録して続行。本体の変更が要る事項は記録して止まる |
| トリアージ（F5 以降） | 定期セッション | reports/triage、ワークフロー定義 | トリアージの判定記録、記述改訂の提案 | なし | 分類体系の変更は常に提案止まり |
| 人間 | 決定者、レビュアー、ラベラー | すべて | decisions.md、承認、ラベル | 利用者セッション、v0.1 と v1.0 の公開 | — |

検証役を実装役から分けるのは、完了条件の判定を実装した当人に任せないため。分布基準の設定、オラクル検証、workflow.yaml の MECE レビュー（人間に出す前の事前確認）は必ず検証役を通す。

### 5.10 動的ワークフローの起動

第5.3節のループは静的で、手順が計画書に書いてある。動的ワークフローは、計画書に書いていない手順をその場で設計し、複数のエージェントに実行させるもの。起動できるのは計画エージェントだけ（利用者セッションは自分の範囲内で可）。

起動してよいのは次の三つの場合に限る。

- 独立に並列化できる作業がある（複数ステージのフィクスチャ生成、負例の作成、ペルソナごとのシミュレータ実行）
- 第三者の視点が要る検証がある（オラクル検証、expectations の妥当性、workflow.yaml の事前レビュー）
- 完了条件を書く前に調査が要る（adopting-gaps の再現、設計の選択肢の比較）

起動前に progress.md に宣言を書く。目的、役割と人数、入力、書いてよいパス、完了条件、予算（トークン、時間、LLM 呼び出し回数）、反復の上限、入れ子の深さ（1 まで）。宣言の無い動的ワークフローは無効で、その成果は受け入れない。

制約。参加エージェントは保護ファイルを書かない。人間へは直接 escalate せず計画エージェント経由にする。結果は静的ループの検証（第5.3節の 4）を通してから受け入れる。動的ワークフローの中でだけ成立する成果（再現できない判断、会話の中の合意）を残さない。残すのはファイルと、それを検証する検査だけ。

終了。成功したら要約を progress.md に、記録を reports/dynamic/\<id>/ に残す。予算超過や完了条件未達は、戻る条件に該当すれば準正常、しなければ例外として扱う。動的ワークフロー自体も三層で判定する。

この制約が強いのは意図的で、動的ワークフローはこのフレームワークが検査できない種類の実行（静的な仕様が無い）だから。計画の中で荷重を負わせず、恒久的な成果は必ず静的な検査に守られたファイルに落とす。ハーネス側で同じ問題がどう扱われるかは決定 #9。

- 進め方: 別セッションで、第7節の二つ目のプロンプトを使う。そのセッションは adopting.md、harness-plan-template.md、examples/toy-minimal/、公開 API の文書だけを読み、フレームワーク本体を修正しない。足りなかったことは examples/software-factory/docs/adopting-gaps.md に書く。通常のセッションがそれを読んで本体を直し（F1〜F3 の成果物へ戻る）、software factory を再検証する。この往復を adopting-gaps.md が空になるまで繰り返す

- 完了条件: workflow.yaml が整合性検査を通り、4フェーズ以上、8ステージ以上、フェーズ境界を越えるロールバック1以上、ユーザー待ちのステージ1以上、実在のツールに裏づけられた決定論指標3以上を含む。参照ランタイムを組み込んで契約適合テストを通す。全ランナーが通る（6種の遷移、確率的偽ステージ本体に対する分布テスト、仕込んだ粗いクラスの検出、(stage, end\_state) のカバレッジ 100%、マルコフ予測と実測の一致、偽の分類器に対するオラクル検証、トリアージの一周）。adopting-gaps.md の全項目が本体側で解消されるか、解消しない理由が decisions.md に記録されている。人間が workflow.yaml をレビューして承認
- 戻る条件 → 戻り先: adopting.md だけでは判断できない事項がある → adopting.md（F2 の成果物）。契約で表せない操作がある → F1 の契約。expectations 形式やランナーで扱えない基準がある → F3。software factory 固有の回避を本体に入れたくなる → 契約の属性か設定項目への一般化（F1）
- 人間ゲート: workflow.yaml のレビュー（goal と end\_state と unknown を合わせたクラス集合が MECE か、記述が成果物から観測可能か、各 end\_state に戻り先があるか。実ハーネスのレビューの予行演習でもある）

### F5 公開と維持

```text
ステージ本体はすべて偽物で、LLM は使いません。決定論的なものは fixtures に用意した成果物をコピーし、確率的なものは種を固定した既知の分布でクラスを出してください。carry を受けた再進入で分布が変わるものと、意図的にクラス内で下流の分布が分かれるものを一つずつ入れてください。実装と単体テストのステージは fixtures の小さなコードベースに対して実際にビルドとテストを走らせ、ビルド通過・テスト通過・カバレッジ・lint・変更パスの範囲を本物の指標として実装してください。要求の取り込みにはペルソナ 3 つ以上のユーザーシミュレータを束縛してください。

フレームワークのランナーをすべて通してください。契約適合テスト、遷移の決定論テスト、分布テスト（expectations を書く）、独立性検証、E2E カバレッジとマルコフ合成、偽の分類器によるオラクル検証、トリアージの一周。

adopting.md と雛形だけでは判断できなかったこと、足りなかったこと、回避したくなったことを、すべて examples/software-factory/docs/adopting-gaps.md に書いてください。回避策を本体に入れてはいけません。サブエージェントを使う場合も、同じ読取制限を課してください。進捗は examples/software-factory/docs/progress.md に書いてください。
```

## 付録 B ステージ定義の例（拡張スキーマ）

toy-minimal と software factory の workflow.yaml はこの形で書く。goal を満たせば次へ進み、end\_state に該当すれば rollback の戻り先へ carry を持って戻り、unknown は人間に差し戻す。複数の end\_state に当てはまりうる場合は記述中の「優先する」に従う。carry の各項目は、元ステージの memory\_out と戻り先の memory\_in の両方に含める。

```yaml
- id: verify
  name: Verify
  description: draft.md の主張を検証し、結果を report.json に書く
  artifacts:
    reads: [draft.md]
    writes: [report.json]
    memory_in: [review_findings]
    memory_out: [failing_checks, missing_inputs]
  goal:
    qualitative: >-
      draft.md の全ての主張が report.json で検証済みとして記録され、
      検証できないものは仮定として明示されている。
    quantitative:
      report_exists:
        description: report.json が存在しスキーマに適合する
        equals: true
      verified_ratio:
        description: 主張のうち検証済みの割合
        min: 0.8
  end_state:
    - id: checks_failed
      description: >-
        一つ以上の主張が検証に失敗している。失敗した検査の一覧が report.json にある。
        この状態は inputs_missing に優先する。
    - id: inputs_missing
      description: >-
        検証に必要な入力が draft.md にも作業ディレクトリにも無い。
        失敗ではなく、検証できていない。
    - id: unknown
      description: 上記に当てはまらない、または分類の確信度が低い。人間に差し戻す。
  rollback:
    - state: checks_failed
      stage: draft
      carry: [failing_checks]
      max: 2
    - state: inputs_missing
      stage: collect
      carry: [missing_inputs]
      max: 1
```

整合性検査器が見るのは、unknown を除く end\_state と rollback.state が一対一に対応すること、戻り先がそのステージより前にあること、全ての rollback に max があり有界であること、carry の各項目が元の memory\_out と戻り先の memory\_in にあること、quantitative の指標名が指標レジストリにあること。end\_state の記述の良し悪し（成果物から観測できるか、互いに排他か）は人間のレビューで見る。
