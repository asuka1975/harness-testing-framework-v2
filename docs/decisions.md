状態の凡例: **提案**（決定待ち）/ **決定** / **先送り**（強制点で決めざるを得なくなる）/ **却下**

## ADR-001 成果物宣言の形

- 状態: 提案（決定待ち）
- 強制点: F1 スキーマ
- 起票: 2026-10-22

### 文脈

ステージは作業ディレクトリ上の成果物を読み書きし、ロールバック時には carry の項目だけを戻り先の開始時スナップショットに重ねる（第2節「ロールバック」）。整合性検査器は「carry の各項目が元ステージの memory_out と戻り先の memory_in にあること」を検査する（付録 B 末尾）。分類器にはスナップショット全体ではなく投影を渡す（第5.6節）。この三つがどこから導出されるかを決める。

### 選択肢と帰結

#### (a) 宣言なし

- スキーマ: 最小。stage に artifacts 属性を持たない
- 検査器: carry の生成と消費を検査できない。carry は自由文字列になり、戻り先が受け取れるかは実行時まで分からない
- ランタイム: checkpoint の範囲が決められず、作業ディレクトリ全体を保存・復元する。overlay は宣言のない鍵を受け入れるしかなく、契約で守れない
- 分類器への投影: 根拠が無い。スナップショット全体を渡すか、ステージごとに場当たりの要約を書くことになる（第5.6節の禁止事項に抵触しやすい）

#### (b) reads / writes のみ

- スキーマ: artifacts に reads と writes（パスの配列）
- 検査器: ファイル単位の依存は検査できる。carry（memory）は依然として検査できない
- ランタイム: checkpoint の範囲は writes で決まる。overlay が何を重ねてよいかの宣言が無く、carry の意味が曖昧なまま
- 分類器への投影: reads ∪ writes で切れるが、持ち帰った情報（失敗したテストの一覧など）が投影に入らない

#### (c) reads / writes に加えて memory_in / memory_out（推奨）

- スキーマ: artifacts に reads / writes（パス）と memory_in / memory_out（鍵）の四つの配列
- 検査器: carry ⊆ 元の memory_out かつ carry ⊆ 戻り先の memory_in を機械的に検査できる
- ランタイム: checkpoint = writes の範囲のスナップショット、restore + overlay = memory 項目だけを重ねる。overlay は memory_in に無い鍵を拒否できる
- 分類器への投影: reads ∪ writes ∪ memory_in から状態文書を組み立てられる
- コスト: ステージ定義の記述量が増える。宣言し忘れは実行時に契約（overlay の拒否、未宣言パスの書き込み検出）で捕まえる

### 推奨

(c)。carry の検査、checkpoint の範囲、投影の三つがすべてここから導出され、他の選択肢ではそのうち少なくとも一つに根拠が無くなる。

### 付随する小決定（推奨どおりなら F1 のスキーマ作業で確定する。異論があればここに書く）

- reads / writes は作業ディレクトリ相対のパス文字列。v1 ではグロブを扱わない（必要が出たら拡張）
- memory の鍵は識別子（`^[a-z][a-z0-9_]*$`）。値の形はスナップショット形式で決める（契約の範囲）
- reads が前方のステージの writes に含まれるかの検査は F1 の検査器の必須性質に含めない（計画書の列挙に無い）。警告として出すかは検査器の実装時に決める
- 四つの配列はすべて省略可で、省略は空と同義にする

## ADR-002 指標レジストリ

- 状態: 提案（決定待ち）
- 強制点: F1 スキーマ
- 起票: 2026-10-22

### 文脈

goal.quantitative は決定論的述語の集まりで、評価順序の最初に判定される（第2節「評価順序」）。software factory ではビルド通過・テスト通過・カバレッジ・lint のような、外部ツールに裏づけられた指標が必要になる（F4）。判定式をどこに置くかを決める。

### 選択肢と帰結

#### (a) 指標の判定式を YAML に書き、コードで解釈する

- スキーマ: 式の文法をスキーマで表す必要がある（式言語の設計がフレームワークの表面になる）
- 検査器: 式の構文は検査できるが、式が参照する外部ツール（ビルド、テスト）の存在は検査できない
- ランタイム: 式の評価器をフレームワークに持つ。外部ツールを呼ぶ指標は結局プラグイン機構が要り、式言語とプラグインの二重構造になる
- 汎用性: 式の中に特定ツールの呼び出しが現れると第5.8節の規律に抵触する

#### (b) YAML には指標名と基準だけ。実装はハーネス側のレジストリ（推奨）

- スキーマ: quantitative の各指標は `description` と `equals` / `min` / `max` のいずれか（付録 A の説明に沿う）
- 検査器: 「YAML が参照する指標名がすべてレジストリにある」を検査する。検査器の入力が YAML だけでなくなる（下記の小決定）
- ランタイム: 契約に Metric インターフェース（名前 → スナップショットを受け取り値を返す）と MetricRegistry（名前の集合と解決）を置く。評価は値と基準の比較だけで、フレームワークは指標の中身を知らない
- 汎用性: 外部ツールはすべてハーネス側に閉じる

### 推奨

(b)。フレームワークに式言語を持ち込まず、指標の存在検査を整合性検査に含める。

### 付随する小決定

- 検査器がレジストリを知る方法: (i) ハーネスのモジュールを import して `names()` を呼ぶ (ii) 指標名を列挙したマニフェストファイルを渡す。推奨は両方を受け付ける（CI で import できない環境のため (ii) を残す）。契約は `names()` を持つ MetricRegistry を定める
- 基準の形: `equals`（任意の JSON 値）、`min` / `max`（数値、両方を同時に書いてよい）。一つの指標に `equals` と `min` / `max` を同時に書くのは負例とする
- **第2節の評価順序に追加する規則（見落とさないこと）**: 指標が値を返せない（ツールが落ちた等）場合は goal 不成立ではなく unknown に落とす。goal 指標の失敗と評価不能を区別する。評価順序（goal 指標 → goal 定性 → end_state → unknown）自体は変えない

## ADR-003 escalate 後の人間の選択肢

- 状態: 提案（決定待ち）
- 強制点: F2 runner
- 起票: 2026-10-22

### 文脈

unknown への分類、確信度の閾値未満、rollback の max 超過は人間へ escalate する。人間が返せる指示の集合を runner が受け付ける形で決める。

### 選択肢と帰結

四つの候補: 再実行 / 指定ステージへロールバック / goal 到達扱いで続行（注記つき）/ 中止。

#### 一部のみ（例: 再実行と中止だけ）

- ランタイム: 単純。中断状態からの復帰は「同じステージを同じスナップショットからやり直す」か「終わる」の二択
- 運用: 人間が原因を見て「設計からやり直したい」「この判定は分類器の誤りなので先へ進めたい」と思っても表現できず、ワークフローの外で手作業することになる。その手作業は記録に残らない

#### 四つすべて（推奨）

- ランタイム: Resolution 型に四つの変種を持つ。`continue_as_goal` は注記（理由）を必須にし、実行記録に人間の上書きとして残す。`rollback_to(stage)` は戻り先の開始時スナップショットの復元で、辺の max を消費しない（人間の操作はワークフロー上の辺ではない）
- テスト: 四つの変種それぞれに決定論テスト（F2 の完了条件「escalate の4つの選択肢が動く」）
- E2E / 分布: `continue_as_goal` を goal 到達とは別に数える（人間の上書きを goal 到達率に混ぜない）

### 推奨

四つすべて。runner はこの四つを受け付け、どれを選んだかを記録に残す。

### 付随する小決定（F2 で確定。先に意見があれば書く）

- 人間の `rollback_to` の戻り先は、escalate したステージより前の任意のステージ（前方性は人間の操作にも適用する）
- 人間の `rollback_to` では carry を自動では重ねない。重ねたい項目は指示に明示する（戻り先の memory_in に無い鍵は拒否）
- `rerun` は同じ開始時スナップショットからの再実行。max の計数には含めない

## ADR-004 ユーザー回答待ちの表現

- 状態: 提案（決定待ち）
- 強制点: F2 runner
- 起票: 2026-10-22

### 文脈

要求の取り込みのようなステージは、途中でユーザーに質問して回答を待つ。これを三層（goal / end_state / unknown）のどこで扱うかを決める。テストではユーザーシミュレータを束縛する必要がある。

### 選択肢と帰結

#### (a) end_state の一つとして持つ

- スキーマ: 「回答待ち」クラスに rollback の戻り先が要る。戻り先は自分自身になり、「戻り先はそのステージより前」という検査器の性質に反する。例外扱いにすると検査器の性質に穴が開く
- 分類: 「回答待ち」は成果物から観測される結果ではなく実行の途中状態で、MECE な結果分類に混ぜると記述が崩れる
- テスト: 回答待ちを踏む経路が E2E のカバレッジ対象（stage, end_state）に紛れ込む

#### (b) runner が中断状態を持ち、ステージ本体はユーザー入出力インターフェースで同期的に待つ（推奨）

- 契約: UserIO インターフェース（質問 → 回答）を追加。ステージ本体は同期的に呼ぶだけで、待ち方を知らない
- ランタイム: UserIO の実装がその場で答えられない時（対話が別プロセスにある等）は runner が「中断」状態に入り、保留中の質問と開始時スナップショットを保存して終了する。回答が来たら再開する
- テスト: UserIO にシミュレータ（ペルソナ）を束縛する。recorder はユーザー回答も記録再生の対象にする
- 分類: 分類器は回答待ちを見ない。三層は結果の分類のまま保たれる

### 推奨

(b)。三層を結果の分類として保ち、待ちは実行機構の状態にする。

### 付随する小決定（F2 で確定）

- 再開の仕組みは「回答を入力列に加えて、ステージを開始時スナップショットから再実行する」を推奨する。ステージ本体は途中状態を持たずに済み、記録再生と相性がよい。回答が揃うまでは何度でも中断しうるので、回答列は累積する
- 一つのステージが出せる質問数の上限を設けるか（無限に聞き続ける本体への防御）は F2 で検討する

## ADR-005 フェーズゲートの意味論

- 状態: 提案（決定待ち）
- 強制点: F1 スキーマ
- 起票: 2026-10-22

### 文脈

付録 A のフェーズは goal（qualitative / quantitative）を持つが、end_state と rollback は持たない。フェーズの goal を実行時にどう扱うか、フェーズ境界を越えるロールバックが通過済みゲートに何をするかを決める。

### 選択肢と帰結

#### (a) フェーズの goal は文書上の説明のみ

- スキーマ: phase.goal は残るが実行時の意味が無い。quantitative はスキーマ上の死んだ属性になる
- ランタイム: フェーズは単なるグループ化。ゲートは無く、境界越えのロールバックも通常のロールバックと同じ
- 検査器: phase.goal.quantitative の指標の存在を検査する意味が無い

#### (b) フェーズの end_state は最終ステージの end_state、quantitative はフェーズ成果物の集約述語。境界を越えるロールバックは通過済みゲートを無効化し、再通過時に再評価（推奨）

- スキーマ: phase に end_state を持たせない（最終ステージのものを使う）。phase.goal.quantitative の指標は同じレジストリの名前で、フェーズ終了時のスナップショットで評価する
- ランタイム: 最終ステージが goal 到達 → フェーズの quantitative を評価 → 通過ならゲート通過を記録。前のフェーズのステージへロールバックしたら、その境界以降のゲート通過記録を無効化し、再び最終ステージを goal で抜けた時に再評価する
- 検査器: phase.goal.quantitative の指標名の存在を検査に含める
- テスト: toy-minimal に境界越えのロールバックを一つ入れ、無効化と再評価を決定論テストで踏む

### 推奨

(b)。phase.goal を実行時に意味のあるものにし、境界越えの扱いを runner に閉じる。

### 付随する小決定

- **第2節の評価順序に追加する規則（見落とさないこと）**: 最終ステージは goal を満たしたがフェーズの集約述語を満たさない場合、フェーズに戻り先が無いので unknown として escalate する。ここに戻り先を付けたい（フェーズ単位の rollback）要件が F4 で出たら、スキーマの拡張として別途起票する
- 評価順序は変えない。フェーズの quantitative はステージの三層判定の後に、goal 到達の場合にだけ評価する
- phase.goal.qualitative は v1 では文書上の説明に留める（分類器には渡さない）。渡したい要件が出たら起票する

## ADR-006 実 LLM による方法検証の場所と分類器の後ろ側

- 状態: 先送り（強制点 F5 で決める。ここには下書きだけを置く）
- 強制点: F5
- 起票: 2026-10-22

### 文脈

フレームワークのテストは LLM を呼ばない（第2節）。方法そのもの（自然言語の end_state を分類器が人間と一致して分類できるか、マルコフ性、carry の収束）の検証は実 LLM を伴う別の作業で、場所を決める必要がある。分類器の後ろ側（Jev または System One アダプタ）も同時に決める。

### 選択肢と帰結

#### (a) software factory の一ステージを実 LLM 化して行う（recorder 経由、フレームワーク内の任意拡張）

- 玩具の中で閉じるので再現しやすく、コーパスと人手ラベルをフレームワークの資産にできる
- software factory は偽ステージ前提で作られるので、一ステージだけ本物にする境界（記録再生、コスト上限）を用意する必要がある

#### (b) 外部の実ハーネスの計画書で行う

- 実データで検証できるが、フレームワークのリポジトリに結果が残らず、雛形（harness-plan-template.md）の初回適用と重なる

#### (c) 両方

- 最も情報が多いが、v1.0 の後の作業量が最大

### 推奨

(a) を v1.0 の後に小さく行う。分類器の後ろ側は System One アダプタ経由の LLM で着手し、Jev（TypeSafe AI、早期アクセス）が使えれば差し替える。閾値はその較正結果で決め、根拠を記録する（第2節「分類器の検証」）。

## ADR-007 end_state の優先順の表現

- 状態: 提案（決定待ち）
- 強制点: F1 スキーマ
- 起票: 2026-10-22

### 文脈

複数の end_state に当てはまりうる状態がある時の優先順をどう表すか。分類器には記述をそのまま選択肢として渡し、分類ロジックをコードに書かない（第2節「分類器」）。

### 選択肢と帰結

#### (a) 記述文中に「〜に優先する」と書く（推奨）

- スキーマ: 変更なし。人間が読む単位（一つの記述）が崩れない
- 分類器: 優先順も記述の一部として渡され、分類器がそのまま解釈する。「記述が分類の全て」が保たれる
- 検査器: 優先順を検査しない（循環や欠落は人間のレビューで見る）

#### (b) 別属性 priority を持つ

- スキーマ: end_state に priority（整数）を追加。検査器が全順序を検査できる
- 分類器: 優先順を分類器の外で適用する（複数候補を返させてコードで選ぶ）か、属性を文に変換して渡す。前者は分類ロジックをコードに書くことになり第2節に反する。後者なら (a) と同じ情報を二つの場所に持つことになる

### 推奨

(a)。人間が読む単位を崩さず、分類器に渡す情報を記述に一本化する。

### 付随する小決定

- 記述の書き方の規約（「この状態は X に優先する」の定型句）を adopting.md と付録 B の例に揃えて書く。規約は検査しないが、レビューの観点に入れる

## ADR-008 ランタイムの置き場

- 状態: 提案（決定待ち）
- 強制点: F2
- 起票: 2026-10-22

### 文脈

フレームワークが契約だけを定めるか、参照ランタイムをライブラリとして提供するか。検査器が保証する性質（戻り先の前方性、max の有界性など）が実行時にも成り立つかはランタイムの実装次第で決まる。

### 選択肢と帰結

#### (a) 契約だけを定め、runner / checkpoint / oracle は各ハーネスが実装

- フレームワーク: 契約とその適合テストだけ。配布物は小さい
- ハーネス: 仕様駆動の実行（YAML を読んで遷移・ゲート・ロールバックを駆動）を毎回再実装する。検査器が保証した性質が実行時に届く保証は契約適合テストだけ
- テストランナー群（F3）: ハーネスごとのランタイムに対して動かす必要があり、ランナー側が契約だけに依存するよう書く

#### (b) 参照ランタイムをライブラリとして提供し、ハーネスは組み込む（推奨）

- フレームワーク: 配布可能なパッケージになる。公開 API のバージョン管理（semver）とハーネス側の依存固定が要る
- ハーネス: ワークフロー定義、ステージ本体、指標、ユーザー入出力、LLM クライアントを提供して組み込む。再実装しない
- 契約適合テスト: 参照ランタイム自身が通す。(a) を選ぶハーネスのためにも残し、ハーネスが契約を満たすかはこのテストでのみ判定する（第5.8節）
- adopting.md: 組み込み方を文書化する

### 推奨

(b)。仕様駆動の実行をハーネスごとに再実装させない。

## ADR-010 言語、ツールチェーン、公開先

- 状態: 提案（決定待ち）
- 強制点: F1 初期化（これが決まるまで pyproject と CI の雛形を作れない）
- 起票: 2026-10-22

### 文脈

言語と依存管理、テストランナー、lint、CI、バージョン公開の方法を決める。初期化時に確認した環境: Python 3.12.3、uv（`~/.local/bin/uv`）あり、システムの Python に jsonschema 4.10.3 と PyYAML 6.0.1 あり、ruff / pytest は未インストール（uv で入れられる）、git 2.43.0、リモートは未設定。

### 選択肢と帰結

計画書の推奨以外の組み合わせ（例: TypeScript、Poetry）は、スキーマ検証とハーネスからの組み込みの両方で Python 系が自然であること、環境に uv が既にあることから、ここでは比較対象に挙げない。異論があれば決定欄に書く。

#### 推奨構成

- 言語: Python 3.12（`requires-python = ">=3.12"`）
- 依存管理: uv（pyproject.toml + uv.lock をコミット）
- テスト: pytest + pytest-cov（F2 の完了条件「runtime の行カバレッジ 90% 以上」を CI で測る）
- lint / format: ruff（lint と format の両方）
- 実行時依存: jsonschema（Draft 2020-12）、PyYAML
- CI: GitHub Actions。段階は F5 で設定（整合性検査と決定論テストは常時、オラクル検証はナイトリー、分布と E2E は手動トリガ）
- 公開: git tag（v0.1、v1.0）と GitHub Release まで。パッケージレジストリ（PyPI 等）への公開は別途人間が決める

### 付随する小決定: パッケージ配置（第4節の木と Python の import 名の対応）

第4節の木は `schema/ contract/ runtime/ testing/` をリポジトリ直下に置く。Python パッケージとしての import 名をどうするか。

- **(P1) 木のとおり直下に置き、`contract` / `runtime` / `testing` を最上位パッケージにする**: 計画書との対応が一対一。ただし import 名が汎用語で、組み込む側のハーネスが同名のディレクトリを持つと衝突する（`testing/` を持つリポジトリは珍しくない）。フレームワーク自身のテストの置き場（`tests/`）が木に無いので追加が要る
- **(P2) 単一の最上位パッケージ（例: `htf`）の下に第4節の名前で置く（`src/htf/contract` など）。`schema/`、`examples/`、`docs/`、`tests/` は直下**: import 名が衝突しない。第4節の三つのディレクトリの実パスが変わるので、対応表を decisions.md に残し、保護ファイルの規定（第5.9節）は実パスで読む
- **(P3) 木のとおり直下に置き、ビルド設定で単一名前空間に写像する**: 見た目と import 名を両立するが、editable インストールで写像が効かない等の罠があり、採用する側に説明しにくい

推奨は (P2)。計画書の木との差は三ディレクトリの実パスだけで、意味は変えない。(P1) を選ぶ場合は `tests/` の追加だけ認めてほしい。

### 推奨

上記の推奨構成と (P2)。
