# 第 1 ターン（指示の前提のまま）

## 1. 全体の判定

**直してから出す。** ビルド・lint・カバレッジ不足などの通常の失敗が unknown にしか進めない箇所、二段のロールバックで修正理由を失う経路、拒否理由に対応しない戻り先があるためです。

観測可能性は、ご指定の「そのステージの writes のスナップショットと memory のみ」を前提に評価しました。この前提と資料の一部には不一致があり、第4節に記載しています。

以下は、実装が実際に誤動作するとの断定ではなく、**定義から防げない、または扱いが定まらない成果物の状態**に対する指摘です。整合性検査器や実装のテストは実行していません。ファイルも変更していません。

## 3. ステージごとの所見

整った成果物を前提に読む限り、**優先順位で解消されていない、明確な goal／end_state 同士の重複は確認しませんでした**。主な問題は、通常の修正可能な失敗が既存の end_state に入らず unknown になることです。

unknown の「確信度が低い」は、他の条件と併存しても契約の閾値判定で処理されるため、それ自体を排他性違反とは扱っていません。

| 親 `review` | blocking の有無は `review.json` だけで判定可能。design と code が混在した場合の優先関係も明示されている。対象 ID・パスの照合と、二種類の状態に入らない blocking 指摘に問題がある。指摘11・14。 |
| 親 `release` | 承認・理由を記録した後の `rejected` 自体は観測可能。元成果物との完全な照合、成果物不備の修復経路、拒否理由に対応する戻り先、不完全回答の扱いに問題がある。指摘08・10・11・18。 |
| 子 `code` | `repo/`・`code.json`・`task` があり、通常の判定材料は観測可能。`test_failures` / `coverage_gaps` の利用も本体説明にある。最初のステージで品質不成立を止めるため、後段の修正ループに到達できない点が重大。指摘01。 |

`analyze` で「基準が不足しているが質問はない」、`unit_test` で「実行対象を収集できず、テスト単位の failed/error の一覧もない」といった成果物は、既存の準正常条件には明確に入りません。こうした状態を例外として人間へ送る方針なのか、自動修復対象にするのかは、通常の失敗状態との境界を明記する必要があります。

`implement` の集約は、定義された子の終わり方について次のように整理できます。

| 子 run の結果の組み合わせ | 親の扱い |
|---|---|
| 一つでも `code.unknown` または `unit_test.unknown` がある | unknown。ほかに修復待ちの子があっても、上に置かれた unknown 規則が優先される。コメントの意図と一致する。 |
| unknown はなく、`unit_test.tests_failing` または `coverage_low` で終わった子がある | `tasks_unfinished`。両方が混在しても同じ状態になるため、二規則の順序による意味の差はない。 |
| 全ての子 run が goal | 親の goal 指標が成立すれば goal。親の goal 定性では追加検査されない。統合固有の不足は指摘05。 |

これは子の**最終的な結果**の集約です。子の最初の `tests_failing` は通常、まず子の rollback を起こし、max 超過に至った結果が親に届きます。また、親の指標が例外を返せば、集約で回復する前に unknown になります。

rollback の基本構造については、親9辺・子2辺の全11辺で、非 unknown の各状態に戻り先が一つあり、全て同一ワークフロー内の前方を指しています。各 carry 鍵は元の `memory_out` と戻り先の `memory_in` にあり、戻り先の説明もその鍵に触れています。問題は宣言の欠落ではなく、指摘07・16の継続性です。

max は `analyze.ambiguous` が2、ほかの各辺が1です。契約上有効ですが、**run 全体の上限**なので、新しい原因でも同じ辺を再利用すると上限を消費します。例えば、一度設計レビューを修正した後、release から戻って生じた別の設計指摘でも、二度目の `review.design_flaw` は max 超過になります。妥当な値かどうかは資料だけでは判断できません。

フェーズについては、定性 goal は分類器に渡されず、最後のステージが goal になった後に、フェーズ内 writes の和集合で数量条件が評価されます。

|---|---|---|
| 親 `discovery` | `intake/`、`requirements.json` | フェーズ固有の問題なし。二つの指標の対象は和集合に含まれる。`analyze` と同じ条件を再確認するため、同ステージの分類不足を補う仕組みにはならない。 |
| 親 `design` | `design.json`、`tasks.json` | `tasks_cover_design` は観測可能。定性記述の対象範囲に指摘19がある。また、定性記述だけでは元要件の欠落を検出できない。 |
| 親 `build` | `tasks/`、`codebase/`、`merge.json` | 指標の観測範囲は問題なし。`merged_build_passed` の再評価だけなので、指摘05の統合の完全性や修復経路は補えない。 |
| 親 `assure` | `verification/`、`review.json` | フェーズ固有の問題なし。`suite_passed` は `review` 単体の writes にはないが、フェーズの和集合には含まれるため観測できる。 |
| 親 `release` | `release/` | フェーズ固有の問題なし。承認は最終ステージの goal 条件で要求されているため、フェーズ数量条件に承認指標が重複していないことだけを欠陥とは扱わない。 |
| 子 `develop` | `repo/`、`code.json`、`unit/` | フェーズ固有の問題なし。単体テストの指標を評価できる。先行する `code` の失敗で到達できない問題は指摘01。 |

指標名については、**同名の指標を別の意味で使っている明確な箇所はありませんでした**。ステージとフェーズで再利用される指標の説明も一致しています。`unit_coverage` と `suite_coverage`、`build_passed` と `merged_build_passed` は、対象範囲の違いに応じて別名になっています。指摘11・12・15は、指標名の使い回しではなく、観測範囲・期待集合・分類器への説明の問題です。

### 2. 訂正で新しく生じる指摘

**20：状態文書の総量に関する取り決めがない。重大度：中、観点：b。**

`verify`・`review`・`release` の `reads` には `codebase/`、子 `unit_test` には `repo/` が含まれる。訂正された規則では、その配下の全ファイルが、各4000文字まで状態文書に入る。

4000文字は一文書全体の上限ではない。ファイル数が増えれば総量も増え、`## writes` の判定結果より前に大量のソースが配置される。指摘17の「一つのファイルの末尾が失われる問題」とは別に、**文書全体を分類器へ供給できる規模と、上限超過時の扱いが定義されていない**。

実際の fixtures が入力上限を超えることや、後方の情報が実際に捨てられることまでは断定しない。

提案は、対象規模に応じた文書総量の上限と超過時の扱いを定めること。本体に必要な `reads` を単純に削除して解決したことにはせず、投影を縮約するなら、必要な証拠を保存する規則として明示する。

**21：reads と writes の不整合に対する分類条件が不足している。重大度：中、観点：a・b。**

原本と生成物の双方が見えるため、両者の食い違いを分類器が観測できる。しかし、次のような場合の修復クラスや優先条件が不足している。

- **`plan`：原本と転記一覧で、goal の母集団が異なる。** 定性 goal は「tasks.json のタスクが design.json の全てのコンポーネントを覆い」、指標は「tasks.json の design_components がすべて、いずれかのタスクの components にある」となっている。原本には C1 だけがあり、タスクは C1 を覆っているが、転記一覧に古い C2 が残っている場合、定性 goal は成立する一方、指標は不成立になる。`uncovered_components` も空なら、契約上は数量条件と分類器の不一致による unknown となり、再計画の経路がない。
- **`verify`：report の成功記録と入力の証拠の優先関係がない。** goal は「verification/report.json に、codebase/ のビルド成功、lint 違反なし」などが「記録されている」ことを要求している。例えば reads のソースに明白な構文不備がある一方、report は成功を記録している場合、report の成功記録だけで goal としてよいのか、入力との矛盾を優先すべきかが選択肢に明記されていない。指標も report から計算されるため、この矛盾を別途解消する保証にはならない。

提案は、原本と転記一覧、検証対象と検証記録の一致を goal 条件に含め、不整合時の扱いを明記すること。必要なら対象の版・入力ダイジェスト・期待 ID 集合を記録する。自動修復対象とする場合は、生成元へ戻せる位置で検出する。明示的な不整合状態を追加・拡張するなら、分類体系は変わる。

なお、**rollback によって古い reads が必ず混入するという新規指摘は立てない**。対象定義の reads はいずれも前段の成果物を参照し、戻り先以降の生成ステージは、後段へ進む際に再実行される。残存する後段の成果物を前段が reads に宣言している箇所もない。再生成漏れや外部更新の証拠がない以上、「復元対象外」という性質だけで版の不整合を断定することはできない。
