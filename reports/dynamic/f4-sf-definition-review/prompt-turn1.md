- `implement-task.yaml`（子。親の `implement` ステージがタスクごとに起動する）

2. `docs/CONTRACT.md`（ランタイムの規則の正本。特に: 分類器に渡る状態文書は何から作られるか、評価順序、ロールバック時の memory と carry の扱い、子ワークフローの集約規則、フェーズの goal の評価）

資料にある規則で判断してください。資料に無いことは推測せず「判定できなかった事項」に書いてください。ツールを走らせる必要はありません（整合性検査器はすでに 0 件です。スキーマや参照の整合ではなく、意味のレビューを求めています）。ファイルは変更しないでください。

## 前提となる規則の要点（資料で確認してください）

- 分類器が見るのは、そのステージの `artifacts.writes` の範囲のスナップショット（状態文書。ファイルごとに先頭 4000 文字で切り詰め）と memory だけです。`reads` のファイルは分類器には渡りません。goal の定性記述・end_state の記述・unknown の記述が分類器に渡る全てで、ステージの `description` は本体への指示です
- 評価順序は固定: goal の指標 → goal の定性 → end_state → unknown。指標が落ちたのに分類器が goal と言えば unknown（不一致）
- ロールバックは、戻り先ステージの開始時点のスナップショット（ファイルと memory）を復元し、`carry` に列挙した鍵だけを上書きします。戻り先は前方（それより前に実行されるステージ）に限られ、ワークフロー（子を含む）の最初のステージは戻り先を持てません
- 子ワークフローを持つステージ（`implement`）では、goal の定性と end_state の記述は分類器に渡らず、`aggregate` の規則が上から順に評価されます。子の unknown（escalate）は子 run の結果として親に届きます
- フェーズの goal はフェーズの最後に、フェーズ内の writes の和集合で評価されます

## レビューの観点

ステージごと（親 8 + 子 2）とフェーズごとに、次を確かめてください。

(a) **MECE**: {goal, 各 end_state, unknown} のクラス集合は網羅的で、互いに排他か。起こりうる成果物の状態で、どのクラスにも当てはまらないもの（unknown に落ちるしかないもの）、二つ以上に当てはまるもの（「〜に優先する」で解消されていないもの）を挙げてください。頻度が高そうな失敗が unknown にしか行けない箇所は重く見てください

(b) **観測可能性**: 各記述（goal 定性、end_state）は、writes のスナップショットと memory だけから決められるか。`reads` のファイルや、本体しか知らないこと、他のステージの成果物を前提にしている記述を挙げてください。指標の `description` が指標の名前と整合しているか、同じ名前の指標が別の意味で使われていないかも見てください

(c) **戻り先と carry**: 各 end_state に戻り先が一つあり、前方か。`carry` の鍵は戻り先の `memory_in` にあり、戻り先の `description` がその鍵の扱いを述べているか。二段続けて戻る経路（例: release → analyze → intake → analyze、review → design → analyze → intake）で、最初の carry が restore で消えて戻り先の再実行に届かなくなる箇所はないか。`max` の値は妥当か

(d) **子の集約**: `implement` の `aggregate` 規則は、子の end_state の組み合わせを網羅しているか。規則の順序で意図と違う結果になる組み合わせはないか。子の `code` が最初のステージで戻り先を持てないことの帰結は何か

(e) **ユーザー待ちのステージ**（`intake`、`release`）: 回答が無い・途中である場合の分類は決まるか

## 出力の形式

次の節立てで、最後のメッセージに完全な報告を書いてください（最後のメッセージがそのまま報告ファイルになります）。

1. **全体の判定**: 人間の MECE レビューに出せる状態か（出せる / 直してから出す / 出せない）と一文の理由
2. **指摘の一覧**: 表。列は「番号 / 重大度（高・中・低）/ 対象（ステージか横断）/ 観点（a〜e）/ 指摘 / 根拠（定義からの引用。行の文言をそのまま）/ 失敗する具体的な場面 / 直すと分類体系が変わるか（end_state の追加・分割・統合・意味変更なら「変わる」、記述の文言だけなら「記述のみ」）/ 提案」。重大度の順に並べてください
3. **ステージごとの所見**: 指摘が無いステージも「問題なし」と一行で書いてください（見落としと区別するため）
4. **判定できなかった事項**: 資料だけでは決められなかったこと
5. **読んだファイルの一覧**

重大度の目安: 高 = 普通の運転で起きる失敗が人間に差し戻されるか、誤った戻り先に行く。中 = 稀だが起きる、または記述が曖昧で分類器がぶれる。低 = 文言の改善。
